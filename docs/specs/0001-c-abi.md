# Spec — C ABI (foobar plugin seam)

> **Subsystem:** The versioned `extern "C"` surface the foobar2000 C++ shim links against — the one seam between a frontend and `core`.
> **Source:** `core-cabi/src/lib.rs` (definitions), `core-cabi/include/lmv_core.h` (C mirror the shim compiles against)
> **Reconciled-through:** Plan 0107 (surface at **v6**; reconciled 2026-08-17).
> [ADR-0117](../adrs/0117-c-abi-v6-the-host-reads-the-roster-and-selects-a-preset.md) added
> `lmv_get_presets` + `lmv_select_preset` — the fourteenth and fifteenth functions — and
> `LMV_ABI_VERSION` moved `5` → `6`, so the foobar menu can list the roster and pick from it instead
> of cycling. Both are thin wrappers over core methods the standalone's browse overlay has used since
> Plan 0008; no new core capability crossed with them. **The surface had widened once before, at
> v5:** [ADR-0110](../adrs/0110-now-playing-is-a-shell-supplied-string-and-the-core-owns-the-banner.md)
> added `lmv_set_now_playing`, the thirteenth function. Widening
> it is the ADR-worthy event the invariant below calls for, not a casual edit. **Paths were re-pointed
> at Plan 0061's close (2026-08-08):** [ADR-0072](../adrs/0072-the-c-abi-ships-from-its-own-crate.md)
> moved the definitions and the header out of `core/` into the `lmv-core-cabi` crate — where it compiles
> changed, the surface did not. Note that `lmv-core-cabi` sits outside the workspace `default-members`,
> so the conformance suite below runs under `--workspace` or `-p lmv-core-cabi` and **not** under a bare
> `cargo nextest run`.
> **Governing ADRs:** [0003](../adrs/0003-c-abi-v1-surface.md) (v1 surface + the freeze rationale), extended by [0006](../adrs/0006-c-abi-v2-preset-loading.md) (v2), [0008](../adrs/0008-c-abi-v3-diagnostics.md) (v3), [0013](../adrs/0013-c-abi-v4-render-dt.md) (v4), [0110](../adrs/0110-now-playing-is-a-shell-supplied-string-and-the-core-owns-the-banner.md) (v5), [0117](../adrs/0117-c-abi-v6-the-host-reads-the-roster-and-selects-a-preset.md) (v6); [0001](../adrs/0001-rust-core-wgpu-cabi-foobar-shim.md) (the seam exists)

## Invariants

- The current surface (`LMV_ABI_VERSION = 6`) MUST be exactly these **fifteen** functions and no
  others: `lmv_abi_version`, `lmv_create`, `lmv_free`, `lmv_push_samples`, `lmv_attach_window`,
  `lmv_render`, `lmv_render_dt`, `lmv_resize`, `lmv_cycle_scene`, `lmv_load_presets`,
  `lmv_get_presets`, `lmv_select_preset`, `lmv_set_debug`, `lmv_get_metrics`,
  `lmv_set_now_playing`. Each addition since v1 carries its own
  ADR: `lmv_load_presets` (v2, ADR-0006), `lmv_set_debug` + `lmv_get_metrics` + `LmvMetrics`
  (v3, ADR-0008), `lmv_render_dt` (v4, ADR-0013), `lmv_set_now_playing` (v5, ADR-0110),
  `lmv_get_presets` + `lmv_select_preset` (v6, ADR-0117).
  (`core-cabi/src/lib.rs`)
- **A preset index is snapshot-scoped, not a stable ID.** An index passed to `lmv_select_preset` is
  an absolute position in the list the *same handle's* `lmv_get_presets` reported, with no
  `lmv_load_presets` in between; a host that persists a choice across runs persists the **name** and
  re-resolves it against a fresh snapshot. Stable IDs are a future ABI decision, not a
  reinterpretation of these. (ADR-0117)
- **A string crossing the boundary MUST be copied on receipt.** `lmv_set_now_playing` copies the
  bytes before it returns and never retains the caller's pointer, so the caller may free or reuse
  the buffer immediately. This is the one rule the C++ side cannot verify and must be able to rely
  on; getting it wrong is a use-after-free that will not reproduce reliably. (ADR-0110)
- `LMV_ABI_VERSION` MUST change **only** when the shape of the `extern "C"` surface changes
  (a signature, a function, an error code) — never as a side effect of an application version
  bump. It is a separate axis from the app version (ADR-0005). (ADR-0003)
- The C header `core-cabi/include/lmv_core.h` MUST match `core-cabi/src/lib.rs` signature-for-signature,
  **including the `LMV_ABI_VERSION` literal and the `LmvMetrics` field layout**; the shim compiles
  against the header separately from the Rust crate, so a drift is a link/runtime error, not a
  compile error. (ADR-0003)
- Every pointer crossing the boundary MUST be validated where it enters the core (null checks,
  handle validity); the hot path downstream trusts it. Validate at the boundary, trust inside.
  (CLAUDE.md non-negotiables)
- A panic MUST NOT cross the boundary: every entry point catches unwinds and maps them to
  `LMV_ERR_PANIC` (`-5`) rather than unwinding into C++. (`core-cabi/src/lib.rs` module doc)
- `lmv_push_samples` MUST NOT allocate, block, lock a contended mutex, log, or do file I/O —
  it runs on the caller's audio-delivery thread. It hands samples to the ring and returns.
  (CLAUDE.md; see [0002-ring-determinism](0002-ring-determinism.md))
- The threading contract MUST hold in both directions: `lmv_push_samples` from at most one
  thread (the host's audio/visualisation thread), every other call from at most one thread (the
  host's UI/render thread), and never concurrently with `lmv_create`/`lmv_free` on the same
  handle. The two roles meet only at the lock-free ring. (`core-cabi/src/lib.rs`, mirrored in the header)
- **No allocation crosses the boundary.** `LmvMetrics` is caller-allocated plain data; it leads
  with `struct_size` + `abi_version` so later fields can append **without** an ABI bump
  (forward-extensible by size). (ADR-0008)
- Widening the surface (a sixteenth function, a changed signature) is an ADR-worthy event, not a
  casual edit. The seam stays minimal: create / free / push / attach / render / resize /
  cycle-scene / load-presets / read-roster / select-preset / debug / metrics / now-playing. **The
  thirteenth was added under exactly that rule** — ADR-0110 first, `LMV_ABI_VERSION` bumped in the
  same phase, and the cost it carried (the `text` feature's cosmic-text tree in the DLL) measured
  against NFR §4 rather than assumed. **The fourteenth and fifteenth were added the same way** —
  ADR-0117 first, and it rejected the conventional four-function enumeration (count / name-at /
  current / select) precisely because two suffice. (ADR-0001, ADR-0003, ADR-0110, ADR-0117)

## Scenarios

- WHEN the C++ shim calls `lmv_abi_version()` THEN it returns `6`, which the shim compares
  against the header's `LMV_ABI_VERSION` as **`core_abi >= LMV_ABI_VERSION`**: it refuses a core
  **older** than the one it was built against and accepts an equal or newer one. Forward
  compatibility is deliberate and it is what the size-guarded `lmv_get_metrics` buys — a newer
  core appends fields the shim does not read, and the functions the shim does call are stable, so
  a version bump does not have to be a lockstep redeploy of the pair. A refusal is not fatal:
  the shim logs to the foobar console and disables preset loading and diagnostics, leaving the
  render path alone.
- WHEN `lmv_create` succeeds THEN it returns an opaque non-null handle that every other call
  (except `lmv_abi_version`) takes as its first argument; WHEN it fails THEN it returns null
  and no handle is leaked.
- WHEN `lmv_push_samples` is called with a valid handle and a sample buffer THEN the samples
  are copied into the lock-free ring and the call returns immediately, without touching the
  render path.
- WHEN `lmv_push_samples` is called with a null handle or null buffer THEN it is rejected at
  the boundary with `LMV_ERR_INVALID_ARG` (no deref of the invalid pointer), not passed inward.
- WHEN `lmv_render_dt(handle, dt)` is called THEN the frame advances by the host's **real**
  elapsed seconds, so animation is frame-rate independent; WHEN the legacy `lmv_render(handle)`
  is called THEN it is exactly `lmv_render_dt(handle, 1.0/60.0)` — the fixed-step wrapper kept
  for v1-era callers (ADR-0013).
- WHEN a render call is made before `lmv_attach_window` THEN it returns `LMV_ERR_NO_WINDOW`
  rather than rendering or panicking.
- WHEN `lmv_load_presets` is called **before** a window is attached THEN the parsed set is held
  pending and installed as soon as `lmv_attach_window` creates the renderer, and the call still
  reports the loaded count (ADR-0006).
- WHEN `lmv_get_presets` is called with `buf_len = 0` (or a null `buf`) THEN it returns the total
  byte count the full list needs and writes **nothing** into the buffer; WHEN it is called with a
  buffer at least that large THEN every installed name is written in roster order as UTF-8, each
  followed by one `0x00`; WHEN the buffer is smaller than the needed count THEN nothing is written,
  so a short buffer never yields a partial list a host could render as the whole roster (ADR-0117).
- WHEN `lmv_get_presets` is called with a non-null `out_current_index` THEN it receives the index the
  show is **going** to — the dissolve's target while a transition is in flight, matching
  `lmv_cycle_scene`'s convention — or `-1` on an empty roster; it is filled on sizing calls too, and
  left untouched when the call returns an error.
- WHEN `lmv_select_preset(handle, i)` is called with an `i` the same handle's `lmv_get_presets`
  reported THEN the show dissolves to that preset exactly as `lmv_cycle_scene` does, and a following
  `lmv_get_presets` reports `i` as the current index immediately rather than when the dissolve
  finishes; WHEN `i` is negative or past the end THEN it returns `LMV_ERR_INVALID_ARG` and nothing
  changes — a stale index is a host bug worth signalling, not worth a wrap or a panic.
- WHEN either v6 call is made **before** `lmv_attach_window` THEN it returns `LMV_ERR_NO_WINDOW`,
  because the roster installs at attach (ADR-0006's pending-set rule) and an empty list would read
  to a user as "this build ships no presets".
- WHEN `lmv_get_metrics` is called with a caller-allocated `LmvMetrics` THEN the core stamps
  `struct_size` with the byte count it actually wrote and `abi_version` with `LMV_ABI_VERSION`,
  so a host built against an older header reads a prefix rather than garbage (ADR-0008).
- WHEN `lmv_set_now_playing` is called with valid UTF-8 THEN the core copies it, fades a banner in
  over the visuals, holds it, and fades it out on its own — the host says *what* is playing and
  never *when to stop*, so there is no clear call and none is needed. The string is conventionally
  `artist - title`; the core splits on the first ` - ` and draws a single line without one.
- WHEN `lmv_set_now_playing` is called with the string that is already set THEN nothing happens and
  the banner does not re-trigger, so a host may call it on every metadata notification it receives.
- WHEN `lmv_set_now_playing` is called with a null handle, a null pointer, a **zero length**, or
  bytes that are not valid UTF-8 THEN it returns `LMV_ERR_INVALID_ARG` at the boundary rather than
  passing them inward; WHEN it is called before `lmv_attach_window` THEN it returns
  `LMV_ERR_NO_WINDOW`. (Zero length is a caller error here, *not* a clear — the Rust-side
  `Renderer::set_now_playing` treats an empty string as "clear", but no host needs that over the
  ABI, because the banner is transient.)
- WHEN `lmv_set_now_playing` is called THEN it MUST be from the host's playback/UI callback and
  **never** from the `visualisation_stream` thread: the copy allocates, which that thread must
  never do. This is the same distinction `lmv_push_samples` draws from the other direction.
- WHEN `lmv_free` is called on a handle THEN all core resources for that handle are released
  and the handle MUST NOT be used again.
- WHEN the `extern "C"` surface must change shape THEN `LMV_ABI_VERSION` is bumped and a new
  ADR records the addition — the app version (ADR-0005) is untouched by this.

## Known gaps / honest nulls

- **Rust-side FFI coverage exists; the C++ shim is still untested in CI.** `core-cabi/tests/ffi.rs`
  (the path moved with ADR-0072; this line said `core/tests/ffi.rs` until Plan 0107)
  drives `lmv_create` → `lmv_load_presets` → `lmv_render_dt` / `lmv_set_debug` /
  `lmv_get_metrics` → `lmv_free` across the boundary, including the null-argument error paths and
  the version handshake. What remains uncovered is the **C++ side**: `plugin-foobar/` is not
  built in CI (it needs the foobar SDK + MSVC), so header-vs-`ffi.rs` drift is caught only by a
  local plugin build.
- **One test attaches a real window, and it can silently skip.** v6's roster surface only exists
  after `lmv_attach_window`, so Plan 0107 added a `#[cfg(windows)]` test that opens a hidden
  `STATIC` window and drives the real attach path — the first coverage that entry point has had.
  When no adapter can present to that window the test **prints a reason and returns green** rather
  than failing, because its subject is the ABI and not the GPU. So a machine where attach fails
  proves nothing about the roster claims, and a CI run is not evidence they hold; the assertions
  ran on a hardware-GPU dev box at the phase's close.
- **The component's size is a dated series, and the series is what to read.** A single before/after
  pair reads as a fact about the component; what a reader needs is the trend, because the cap is
  what the trend runs into. Release x64, measured on the dev box, against NFR §4's ~10 MB soft cap:

  | Measured at | `foo_lmv.dll` — **the shipped component** | `lmv_core_c.dll` — cdylib, built not shipped | Moved by (shipped) |
  |---|---|---|---|
  | Plan 0097, before `text` | 6,774,784 B | 6,720,512 B | — |
  | Plan 0097, after `text` | 8,879,104 B | 8,824,320 B | +2,104,320 B (+31.1 %) |
  | 2026-08-18, Plan 0107's close | 9,279,488 B | 9,218,048 B | +400,384 B (+4.5 %) |
  | 2026-09-01, Plan 0141 Phase 2 | 9,789,952 B | 9,714,688 B | +510,464 B (+5.5 %) |

  The `text` step is the largest single one and it bought a font system: `core-cabi` enables
  `lmv-core/text` so the banner has one at all (ADR-0110 rejected the 31-glyph quad font, which
  cannot spell `Björk` and fails by painting a silent blank). ADR-0110's Alternative A stays unused.

  **The headroom is 210,048 B.** NFR §4 says "~10 MB" without naming a unit; on the decimal reading
  (10,000,000 B) that is what remains, and on the binary reading (10,485,760 B) it is 695,808 B.
  The tighter reading is the one to plan against, and on it the shipped component is at **97.9 % of
  cap**.

  **Read that percentage as a direction, not a budget.** NFR §4's cap is written *"~10 MB for the
  standalone release exe; plugin DLL in the same ballpark"* — the tilde is deliberate, and the
  plugin is covered by "ballpark" rather than by a number of its own. So 210,048 B is not 210,048 B
  of permission; what the figure says is that this component is close enough to the cap that the
  next reader adding code should measure rather than assume, which is the whole reason the row
  exists. Whether ~10 MB is still the right cap, and whether the plugin should carry its own, are
  questions for NFR §4 and nothing here argues them.

  Neither movement after the `text` step was attributed as it landed. The first is attributed
  below, after the fact; the second is not attributed at all.

  Note which number governs: the shim links the **staticlib** into `foo_lmv.dll`, so the cdylib is a
  proxy — close here, but not the artifact NFR §4's plugin cap is about.

  **Where the growth after Plan 0097 came from.** Bisected 2026-09-01 by building only `core-cabi`
  at four points and reading `lmv_core_c.dll`, every point built the same way so the deltas compare:

  | Point | `lmv_core_c.dll` | Moved by |
  |---|---|---|
  | Plan 0097's close (`34d3c2e`) | 8,822,784 B | — |
  | Release after Plan 0102's close (`9df7ffb`) | 8,822,784 B | **0 B** |
  | Release after Plan 0100's close (`cea366d`) | 9,198,592 B | **+375,808 B** |
  | Plan 0107's close (`22bb460`) | 9,204,736 B | +6,144 B |

  **Plan 0100's MilkDrop conversion work is 98.4 % of that window** — 375,808 B of 381,952 B — and
  the suspicion that named it is confirmed rather than assumed. Plans 0105, 0099 and 0102 together
  moved **nothing measurable**, and Plans 0101, 0108 and 0107 together moved 6,144 B, which
  independently confirms Plan 0107 was not the cause. Nothing here is over cap and nothing is being
  repaired: the MilkDrop runtime is shipped capability and this only says what it weighs.

  **What the bisect establishes about `rust-lld`, and what it does not.** This machine links Rust
  output with `rust-lld` (ADR-0147, a machine-local override adopted 2026-08-29) and every row above
  the last predates it, so the cdylib column spans two linkers. Rebuilding Plan 0097's baseline
  under the override lands **1,536 B from the number recorded at that plan's close** — no
  linker-sized effect at that point. That is one point, and it is not enough to call the column one
  series, because the *other* point that can be checked the same way disagrees by far more: the
  series table records **9,218,048 B** at Plan 0107's close and rebuilding `22bb460` gives
  **9,204,736 B**, a gap of **13,312 B** under the same `cargo build --release -p lmv-core-cabi`.
  Where that gap comes from is **not established** — the linker override is one candidate and the
  `rustc` version in use on each date is another, and neither was recorded at the time, so neither
  can now be ruled in or out.

  **So the working noise floor for this column is ~13 KB, and two numbers above sit under it.** The
  `+6,144 B` row is one of them: it is consistent with Plan 0107 having added nothing, which is what
  its own diff shows, but it does not *measure* that and should not be quoted as if it did. The
  `+375,808 B` attribution is two orders of magnitude clear of the floor and is unaffected.
  `foo_lmv.dll` never had the linker question at all: MSVC `link.exe` links it from the staticlib
  either way.

  **A future bisect should record its `rustc -V` alongside the bytes.** It costs one line at bisect
  time and it is the difference between a gap that can be reasoned about and one that cannot.

  **Re-measure at every release, not when a dependency is added.** A dependency-shaped trigger
  cannot catch this growth and did not: everything after Plan 0097 arrived as code added to `core/`
  behind the ABI, with no new crate anywhere. The release is the trigger that fires without anyone
  remembering, because `packaging/foobar/build-component.ps1` produces the shipped DLL on every
  `v*` tag — the number already exists at that moment. Add a row when it has moved more than
  ~100 KB since the last one.

  **The trigger is written down where a releaser will meet it**, in
  [`docs/releasing.md`](../releasing.md) — a trigger stated only here would be the same defect as
  the dependency-shaped one it replaces, since nobody opens the C ABI spec to cut a release.
  Nothing *mechanically* reads the size yet: the recipe never looks at its own output's `Length`
  (see [design-backlog 0177](../design-backlog.md)). Until it does, this remains a duty a person
  performs, and the honest reading of the table above is that it is only as current as the last
  person who remembered.
- **The header is a hand-maintained mirror.** Nothing mechanically checks
  `core-cabi/include/lmv_core.h` against `core-cabi/src/lib.rs` (no `cbindgen`, per ADR-0003's
  keep-it-small posture). The invariant above is enforced by review, not by a gate.
- This spec covers the *contract shape and boundary discipline*, not the per-call payload
  semantics of rendering (frame timing, surface format) — those live with the render/scene
  subsystem and the wgpu layer.
